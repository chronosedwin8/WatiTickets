01 Resumen ejecutivo

Una plataforma ITSM completa en CRUD, con deuda concentrada en seguridad y pruebas

TicketWati cubre el ciclo ITIL de una mesa de ayuda: incidentes, problemas, cambios, catálogo de servicios, activos/CMDB, órdenes de trabajo, base de conocimiento, desarrollo ágil y gestión de ausencias — todo aislado por tenant_id con Row-Level Security. El frontend es una SPA React madura (rutas lazy, React Query, TipTap, Recharts) y el backend se apoya íntegramente en Supabase (PostgreSQL + Auth + Edge Functions Deno) más Amazon S3/SES para adjuntos y correo entrante.

Sólido

CRUD completo de los 14 módulos, motor de SLA con triggers, integración de email SES/SNS con validación de firma, adjuntos S3 vía presigned URLs, RBAC con 7 roles y permisos de menú.

A medias

Búsqueda global (UI sin backend full-text), notificaciones en tiempo real (campana estática), aprobadores CAB persistidos en localStorage, migraciones vacías en el repo.

Riesgo

Políticas RLS USING(true) que exponen datos entre inquilinos, credenciales en texto plano, sin pruebas automatizadas (0 tests), XSS almacenado sin sanitizar.

Lo primero para el nuevo dev: antes de cualquier feature, atender los hallazgos P0 de la sección Seguridad — hay una fuga de datos cross-tenant explotable con la clave pública y credenciales que deben rotarse. El resto del sistema es una base excelente sobre la que construir.

03 Arquitectura

Cómo encajan las piezas

Arquitectura serverless: el navegador habla directo con PostgREST (Supabase) para el CRUD, y con Edge Functions solo cuando se necesitan credenciales de servidor (S3/SES) o lógica privilegiada.

Frontend

  • Estructura — src/pages/ (una carpeta por módulo, ~20.5k líneas), src/components/ (ui, layout, comunes — ~2.4k), src/lib/api/ (capa de datos modularizada por dominio — ~2.2k), src/contexts/ (Auth y Tenant).
  • Autenticación — AuthContext gestiona sesión Supabase, perfil y tenant. ProtectedRoute/PublicRoute controlan acceso. TenantContext es hoy un wrapper delgado que deriva de Auth (refactor de auditoría).
  • Capa de datos — objetos *Api (ticketsApi, assetsApi, analyticsApi…) encapsulan las consultas Supabase. Casi todas reciben tenantId y filtran por él en el cliente.
  • Rendimiento — code-splitting por ruta con lazy(), caché de React Query, ErrorBoundary global.

Backend (Supabase)

  • PostgreSQL — 53 tablas, 134 claves foráneas, 24 triggers y ~25 funciones (muchas SECURITY DEFINER para analítica: get_mttr, get_fcr_rate, get_csat_score, get_dashboard_stats, get_sprint_velocity…).
  • RLS — Row-Level Security activo en las 53 tablas, con 112 políticas. El aislamiento se apoya en get_my_tenant_id() y comprobaciones de rol contra profiles (ver salvedades en Seguridad).
  • Auth — Supabase GoTrue. 8 cuentas actuales. Roles: admin, owner, manager, agent, technician, developer, customer.

06 Completo vs. pendiente

Lo que está listo y lo que falta

Implementado y funcionando

  • CRUD completo de los 14 módulos con relaciones y filtros por tenant.
  • Motor de SLA: cálculo por prioridad, triggers de timestamps, indicadores de riesgo en UI.
  • Integración de correo entrante con validación criptográfica de firma SNS y parseo MIME.
  • Adjuntos en S3 con credenciales 100% del lado servidor (presigned URLs).
  • RBAC con 7 roles + permisos de menú configurables por rol.
  • Analítica ITSM (MTTR, FCR, CSAT, velocidad de sprint) vía funciones de BD.
  • Editor de texto enriquecido (TipTap), lazy-loading por ruta, Error Boundary global.
  • Build con type-check limpio (tsc -b pasa sin errores).

Pendiente o incompleto

  • Búsqueda global (Ctrl+K): la UI existe en la barra superior, falta el backend full-text multi-entidad.
  • Notificaciones en tiempo real: la campana es estática; no hay canal Supabase Realtime conectado.
  • Aprobadores CAB: persistidos en localStorage en vez de una columna JSONB en changes.
  • Motor de workflows: el sistema es CRUD puro; no hay reglas ni estados condicionales automatizados.
  • Adjuntos de correo entrante: el parser no sube adjuntos a Storage todavía.
  • Pruebas automatizadas: 0 tests en todo el repositorio.
  • Migraciones: los archivos aplicados en supabase/migrations/ están vacíos (0 bytes) — el esquema no se puede reconstruir desde el repo.
  • Grupos de activos: alguna acción marcada como “Próximamente” (botón deshabilitado).
07 Seguridad

Hallazgos de seguridad

Verificados directamente contra la base de datos en producción y el código. Las auditorías internas (docs/audits/) califican la seguridad en 9.5/10, pero esa cifra no se sostiene: existe una fuga de datos entre inquilinos activa. Orden por severidad.

SEC-01

Fuga de datos cross-tenant vía políticas RLS USING(true)

Crítico

Las tablas tickets, profiles, assets, work_orders, tenants y locations tienen políticas SELECT permisivas allow_public_read_* con USING(true) para el rol public. En PostgreSQL las políticas permisivas se combinan con OR: aunque existan políticas correctas por tenant, esta las anula y concede lectura a cualquiera con la clave anónima —que viaja pública en el bundle JS— sobre los datos de todos los inquilinos. Se filtran nombres, emails, roles, asuntos de tickets y activos de toda organización que use la plataforma.

CorrecciónEliminar las políticas allow_public_read_* y reemplazarlas por USING (tenant_id = get_my_tenant_id()), revocando SELECT al rol anon donde no aplique. Auditar las 21 políticas con true detectadas.
SEC-02

Credenciales en texto plano dentro del proyecto

Alto

datos.md (sí está en .gitignore) contiene la service_role key de Supabase, claves de acceso S3 y SES, la contraseña de la BD y contraseñas de usuarios en claro. Además .env no está en .gitignore y docs/SES/ repite secretos. La service_role key salta RLS por completo.

CorrecciónRotar todas las credenciales expuestas (BD, service_role, anon, S3, SES, contraseñas de usuario). Añadir .env y docs/SES/ a .gitignore. Mover secretos a un gestor (Supabase Vault / variables de entorno del proyecto).
SEC-03

Secretos S3/SES almacenados en claro en tenant_settings

Alto

Las columnas s3_secret_key y ses_secret_access_key guardan las claves AWS sin cifrar. Cualquier admin del tenant (o quien explote SEC-01) puede leerlas. La función get_ses_credentials() es SECURITY DEFINER y las devuelve a las Edge Functions.

CorrecciónCifrar con Supabase Vault (pgsodium) o mover las credenciales a secretos de Edge Function por tenant, no a columnas legibles.
SEC-04

XSS almacenado: HTML sin sanitizar

Medio

Se renderiza contenido de la BD con dangerouslySetInnerHTML en 6 vistas (ticket.description, comment.content, article.content…) sin DOMPurify. Aunque el editor es TipTap, el contenido puede inyectarse por la API (varias políticas de INSERT aceptan WITH CHECK (true)), volviéndolo explotable.

CorrecciónSanitizar con DOMPurify antes de inyectar HTML, con una allowlist de etiquetas/atributos coherente con TipTap.
SEC-05

Auto-registro crea inquilinos sin control

Medio

tenants_insert_authenticated tiene WITH CHECK (true): cualquier usuario autenticado puede crear organizaciones y perfiles. El flujo signUp lo permite. Facilita abuso y contaminación de datos.

CorrecciónRestringir la creación de tenants a un flujo de invitación/aprovisionamiento controlado; endurecer el WITH CHECK.
SEC-06

Edge Functions sin rate-limiting ni anti-spam robusto

Bajo

process-inbound-email documenta como TODO el rate-limiting por tenant y una detección de spam/bucles más sofisticada. Riesgo de abuso/DoS por correo.

CorrecciónAñadir límite de tasa por tenant y refuerzo anti-loop antes de exponer SES a producción real.
Nota positiva: el diseño base es correcto —RLS activo en las 53 tablas, credenciales AWS fuera del navegador, firma SNS validada criptográficamente y funciones analíticas con SECURITY DEFINER acotadas. Los hallazgos son configuraciones a corregir, no un rediseño.
08 Deuda técnica

Calidad de código

Métricas

  • 0 pruebas automatizadas (sin Vitest/Playwright).
  • ~102 usos de any — tipado que se relaja en puntos calientes.
  • ~134 console.* restantes (la mayoría tras import.meta.env.DEV).
  • Componentes muy grandes: TicketDetail 1.348, AssetDetail 903, TechnicalSpecs 735 líneas.

Riesgos estructurales

  • Migraciones vacías: la carpeta migrations/ tiene archivos de 0 bytes; el esquema real solo vive en la nube. Riesgo alto de drift.
  • Migraciones duplicadas en migrations_backup/ (p.ej. dos 017_*).
  • Estilos inline mezclados con Tailwind (SettingsPage).
  • Listas sin paginación: ticketsApi.getAll trae todos los tickets del tenant de una vez.
09 Recomendaciones

Hoja de ruta priorizada

Ordenada por prioridad. P0 = antes de exponer a usuarios reales; P3 = mejora incremental.

P0

Cerrar la fuga cross-tenant y rotar credenciales

Reescribir las políticas RLS USING(true) (SEC-01), rotar todos los secretos (SEC-02), y añadir .env a .gitignore. Sanitizar HTML con DOMPurify (SEC-04).

P1

Proteger secretos y aprovisionamiento

Cifrar claves S3/SES con Vault (SEC-03), restringir la creación de tenants (SEC-05) y añadir rate-limiting a las Edge Functions (SEC-06).

P1

Reconstruir las migraciones

Generar migraciones reales desde el esquema actual (supabase db diff) para que la BD sea reproducible y versionada. Consolidar los duplicados de migrations_backup/.

P2

Introducir pruebas

Vitest para la capa src/lib/api/ y utilidades; Playwright para los flujos críticos (crear ticket, aprobar cambio, subir adjunto). Empezar por el motor de SLA.

P2

Optimización de rendimiento

Paginar/virtualizar listas grandes (tickets, activos), asegurar índices en tenant_id, FKs y status, y dividir los componentes de +800 líneas en sub-componentes.

P2

Persistir lo que hoy vive en el cliente

Mover los aprobadores CAB de localStorage a una columna JSONB en changes; habilitar los adjuntos de correo entrante hacia Storage.

P3

Notificaciones y búsqueda en vivo

Conectar Supabase Realtime a la campana de notificaciones; implementar búsqueda full-text multi-entidad reutilizando el trigger ya existente en kb_articles.

P3

Motor de workflows

Reglas y estados condicionales (escalado automático, matriz impacto×urgencia) para pasar de CRUD a automatización ITIL — es el gran salto de valor del plan-futuro.md.

10 Puesta en marcha

Arrancar el proyecto

Variables de entorno (.env)

# Frontend (Vite) — expuestas al navegador
VITE_SUPABASE_URL=https://<project-ref>.supabase.co
VITE_SUPABASE_ANON_KEY=<anon-key>
# CLI / despliegue de funciones
SUPABASE_ACCESS_TOKEN=<access-token>

Comandos

npm install
npm run dev        # Vite dev server → http://localhost:3000
npm run build      # tsc -b && vite build
npm run lint       # ESLint
npm run db:types   # regenerar src/types/database.ts desde el esquema
supabase functions deploy   # desplegar las 5 Edge Functions

Restaurar el backup en Postgres local

El respaldo completo se entrega en la carpeta backup/. Restauración de un comando (Git Bash):

cd backup
PGPASSWORD=1004 ./restaurar_local.sh ticketwati

Incluye ticketwati_full.sql (esquema+datos), ticketwati_full.dump (formato custom), variantes solo-esquema / solo-datos, auth_users_data.sql (8 cuentas) y 00_prep_roles.sql (roles Supabase para restauración limpia). Verificado: 53 tablas, 134 FKs, 71 funciones, 112 políticas, 24 triggers, 451 filas.

Bloqueo de infraestructura a resolver aparte del código: los registros MX del dominio del colegio apuntan a Microsoft 365. Mientras SES no reciba el correo (reenvío o subdominio dedicado tickets.dominio.edu), la creación de tickets por email no se activará aunque el código esté correcto.
